# ZIPPOP 대기열 인증 토큰 시연 시나리오

## 목적

고객 로그인부터 예약 대기열 진입, WebSocket 상태 갱신, 대기자 승격, 예약 취소와 토큰 폐기까지를 소스코드 기준으로 시연한다. 토큰 원문은 화면·GIF·로그에 노출하지 않고 앞 4자리와 뒤 4자리만 필요할 때 표시한다.

## 사전 조건

- Docker Compose로 backend, frontend, MariaDB, Redis가 실행 중이어야 한다.
- 고객 계정: `demo_jiwoo` / `1234`
- 성공 시연용 예약은 현재 시각 이후의 시작·종료 시간을 사용한다. 만료된 시드 예약은 `7019/7020` 검증용으로만 사용한다.
- 대기열 정원보다 먼저 접속한 고객 1명과 대기 고객 1명을 준비한다.

## 시연 순서

### 1. ATOKEN 발급

1. `/login`에서 고객 계정으로 로그인한다.
2. 로그인 응답의 `Set-Cookie`에서 `ATOKEN`이 생성되는지 확인한다.
3. 이후 API 요청은 같은 브라우저 쿠키를 유지한다.
4. 검증: ATOKEN 없이 보호 API를 호출하면 `401`, 업체 계정으로 고객 API를 호출하면 `403`이어야 한다.

### 2. 예약 대기열 등록

1. 예약 상세에서 **대기열 입장하기**를 선택한다.
2. `GET /api/v1/reserves/{reserveIdx}/enrollment`를 호출한다.
3. Redis working 정원이 남아 있으면 응답과 함께 `WTOKEN` 쿠키(10분)를 발급하고 `Authorization: Bearer ...` 헤더를 반환한다.
4. 정원이 가득 차면 응답에 대기 순번만 반환하고 WTOKEN은 발급하지 않는다.
5. 시연 화면에는 `access=0`, 현재 접속자 수, 대기자 수, 현재 순번을 표시한다.

### 3. WebSocket 상태 갱신

1. ATOKEN 쿠키로 SockJS `/ws`에 연결한다.
2. STOMP를 `/user/queue/reserve/status`에 구독한다.
3. `/pub/reserve/status`로 `{"reserveIdx": <id>}`를 전송한다.
4. 10초 주기로 같은 메시지를 보내고 응답의 `access`와 `statusMessage`를 갱신한다.

| access | 의미 | 화면 동작 |
|---:|---|---|
| 0 | 대기 중 | 대기번호 오버레이 유지 |
| 1 | 입장 가능 | 오버레이 닫기, 상품 선택 허용 |
| 2 | 예약 시간 종료 | 종료 안내 후 목록 이동 |
| 3 | 예약 마감 | 마감 안내 후 목록 이동 |

### 4. 대기자 승격 및 WTOKEN 수신

1. working 고객이 예약을 취소하거나 이탈한다.
2. 서버가 waiting 첫 순번을 working으로 이동한다.
3. 승격 고객은 `/user/queue/reserve/status`에서 `access=1`과 `wtoken`을 수신한다.
4. 브라우저는 WTOKEN을 600초 동안 저장하고 상품 선택 화면으로 이동한다.
5. 토큰 문자열은 캡처하지 말고 `WTOKEN=abcd…wxyz`처럼 마스킹한다.

### 5. 취소·폐기 검증

1. 고객이 대기 취소를 누르거나 `beforeunload`가 실행되면 `DELETE /api/v1/reserves/{reserveIdx}/enrollment`를 호출한다.
2. working 고객의 WTOKEN은 Redis blacklist에 등록되고 쿠키는 Max-Age=0으로 삭제된다.
3. 대기 고객은 승격 알림을 받아 즉시 `access=1`이 된다.
4. 취소된 WTOKEN으로 재호출하면 예약 접근이 거부되어야 한다.

## 오류 시나리오

| 상황 | 기대 결과 |
|---|---|
| ATOKEN 없음/만료 | HTTP 401, 로그인 화면 이동 |
| 고객 외 권한으로 enrollment 호출 | HTTP 403 |
| 대기열 등록 없이 status 전송 | `RESERVE_ACCESS_FAIL`(7013 계열) |
| 예약 시작 전/종료 후 호출 | 7019/7020 |
| 취소 후 기존 WTOKEN 재사용 | blacklist 검증 실패 |

## 팝업 스토어 CRUD 기준

대기열 시연에 사용하는 팝업은 업체가 CRUD로 준비한다. 팝업 스토어의 소스 엔드포인트는 다음과 같다.

| 작업 | HTTP | 엔드포인트 | 권한/검증 |
|---|---|---|---|
| 생성 | POST | `/api/v1/popups` | 업체, multipart `req` + 선택 `files` |
| 단건 조회 | GET | `/api/v1/popups/{popupIdx}` | 공개 |
| 목록 조회 | GET | `/api/v1/popups?status=&keyword=&page=&size=` | 공개 |
| 수정 | PATCH | `/api/v1/popups/{popupIdx}` | 소유 업체, multipart `req` + 선택 `files` |
| 삭제 | DELETE | `/api/v1/popups/{popupIdx}` | 소유 업체 |

생성 후에는 예약 시간을 미래로 설정하고 예약 정원(`reservePeople`)을 확인한 뒤 대기열 시나리오를 실행한다. 팝업에 연결되는 굿즈도 동일하게 생성·조회·수정·삭제(`POST/PATCH/GET/DELETE /api/v1/goods`) 검증을 수행한다.
